# ViewFit · 随屏：验证范围与已知限制

ViewFit 目前是开发预览工具。以下区分实现行为、自动化测试和实机验证，避免把程序没有报错误认为其他应用已经完成缩放。

## 自动化验证

| 检查 | 数量 | 覆盖范围 |
| --- | ---: | --- |
| Swift 测试 | 18 | 配置归一化、内屏恢复目标、暂停行为、状态过期、单次尝试锁定、有界微信缩放及取消 |
| Chrome 扩展测试 | 7 | 精确缩放、恢复 100%、去重、禁用、受限制页面隔离、异步操作期间切换配置 |
| 本地通信集成检查 | 4 | 分片消息解析、状态主动推送、过期状态禁用、标准输入关闭后退出 |

运行命令见项目 [README](../README.md)。这些测试不要求显示器插拔，不证明 macOS 权限或其他应用的界面行为一定符合预期。

## Chrome

通过扩展的 `tabs.setZoomSettings` 和 `tabs.setZoom` 设置每个标签页的比例。内部页面或其他受限制页面可能拒绝缩放，单个页面失败不应影响其他标签页。

本地连接显示已连接，只能证明扩展与本地组件通信正常。完整验收还应检查已有网页、新标签页、导航后的网页以及多个 Chrome 用户配置文件。

## Codex

通过 Accessibility 查找原生 View 菜单中的放大、缩小和实际大小命令。设置界面提供 100–200%，每档 10%，恢复操作以 100% 为基准，不修改应用的私有偏好设置。

Codex 的缩放菜单可能根据焦点作用于内置浏览器，而不是整个应用界面。ViewFit 会检查聚焦元素的祖先是否暴露 HTTP(S) URL，检测到时停止调整；该检查不保证识别所有内嵌浏览器状态。先点击对话区域，再手动应用规则，是当前建议的恢复方式。

## 微信

微信的原生菜单提供放大和缩小，但未发现可靠的百分比读取或重置入口。因此 ViewFit 提供「基准、放大一档、放大两档」，不声称这些档位等于 100%、110% 或 120%。内部数值仅用于保存档位。

曾通过手动菜单操作验证放大两档再缩小两档可以回到初始最小档位。当前适配器已改为向微信进程发送成对的 Command± 按键，不打开顶部菜单：

- 只在微信处于前台时执行；每次按键前后检查前台状态和取消状态。
- 回到基准最多执行两次缩小。若仍无法确认基准，停止并显示错误，不继续按键或放大。
- 同一配置请求开始后即记录为已尝试；失败、应用切换和轮询不会自动启动同一个请求。新配置或手动点击「应用当前规则」才能重新尝试。

回归测试模拟了持续 60 秒的前台轮询和未更新的微信菜单状态，断言只尝试一次，最多执行两次缩小。这覆盖了旧版持续弹菜单的重复尝试模式。

**尚未完成当前定向按键方案的实机验收。** 按键发送接口没有送达确认，隐藏菜单的可用状态也可能滞后。「缩小可用」只能证明至少放大一档，不能独立证明恰好放大两档；状态标签也不能代替实际界面观察。

## 待完成的实机验收

1. 微信保持前台，连接外接屏，确认实际放大到配置的档位。
2. 拔掉外接屏，确认恢复基准；在操作完成后手动打开菜单刷新状态，检查缩小命令不可用。
3. 保持微信前台至少 60 秒，不修改配置或手动应用，确认没有再次发送缩放操作、反复弹菜单或继续改变字号。
4. 覆盖合盖外屏、镜像显示、睡眠恢复以及操作中切换应用的情况。

目前未完成上述硬件事件到应用缩放的完整验收。暂停或退出工具会保留当前应用缩放，不会恢复此前任意手动设置。
